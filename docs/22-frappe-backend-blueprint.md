# MaxPro — proposed Frappe backend blueprint

Decision: **2026-11-13, Phase 5**. Next.js 16 / React / TypeScript frontend; a custom **Frappe Framework application** owns future persistence, authentication, role permissions, Python business controllers/services/whitelisted methods and background workers. This decision supersedes earlier NestJS/Fastify/BullMQ/OIDC proposals in historical reports and the architecture examples in the unchanged Gemini PRD. No Frappe app, Python service, schema, database connection, auth or production API is implemented or authorized by this phase. Independently verify and pin a supported Frappe release and database before the separately authorized backend implementation; do not assume PostGIS or an independent Node backend.

## Proposed authoritative records and relationships

All business records below are proposed Frappe DocTypes. Every tenant record carries an indexed Organization link; all linked records must belong to that same organization. Names are illustrative until schema review. Use integer minor currency units, explicit currency and timezone-aware timestamps. Arabic/English fields retain their original language and source provenance.

| DocType | Relationships / essential fields | Authority and validation |
|---|---|---|
| MaxPro Organization | name EN/AR, type landlord/broker/agency, country, legal business/license references, branding, requested domain, verification status | Authoritative business profile; license evidence/access reviewed separately; country policy version |
| MaxPro Membership | Organization + Frappe User, role, invitation status, availability, revision | Separate identity from multi-organization membership; unique org/user; invitation expiry, last-owner protection, seat reservation |
| MaxPro Property | Organization, bilingual canonical facts, rent/sale/payment terms, location, permit/owner evidence references, revision, lifecycle | Authoritative canonical record; source review is separate from moderation, publication or legal verification; immutable revision snapshots |
| MaxPro Property Media | Organization + Property, private File/object reference, room, order, processing/scan state, checksum | Validate parent org; no raw binary in API DTO; processing never invents availability or rights |
| MaxPro Connector Configuration | Organization + shared connector definition/version, authorization state, capability/region contract, server secret reference | Only officially authorized APIs/feeds; credentials encrypted server-side, never in Next/localStorage; schema/rights review |
| MaxPro Publishing Job | Organization + Property/revision + Connector Configuration, approval receipt, mapping version, idempotency key, attempt children, acknowledgement | Immutable payload snapshot; one destination per job; local approval/queue/remote acceptance distinct; retries/reconciliation preserve history |
| MaxPro Lead | Organization + Property, original provider/event ID, normalization, assignment, qualification/stage, consent references, campaign reference | Unique organization/source/event identity; dedupe plus atomic assignment; sensitive identity stored under privacy policy |
| MaxPro Conversation | Organization + Lead, message children or linked Message records, consent, owner, delivery/receipt references | Preserve first touch; official messaging rules and authenticated handover; timestamps come from verified intake |
| MaxPro Viewing | Organization + Lead + Property + Membership, start/end/timezone, requested/confirmed/completed/cancelled | Availability/conflicts checked atomically; separate local request from external calendar confirmation |
| MaxPro Campaign | Organization + Property/revision + approved media, platform, bilingual creative, policy version, objective, schedule, separate budget/service fee, revision | No guessed remote capabilities; factual grounding; budget/targeting/creative changes invalidate approval receipts |
| MaxPro Campaign Approval | Organization + Campaign/revision + Property/revision, decision type, authorized actor, approved budget, policy/config/entitlement fingerprints | Server-generated ordered policy/advertiser/optional admin approvals; no client-supplied actor authority |
| MaxPro Plan | Published illustrative/approved terms, effective version, currency/monthly price, negotiated limits | Admin-only versioned configuration; no retrospective mutation of real invoices; final prices need business approval |
| MaxPro Entitlement | Plan version or negotiated subscription grant, feature, quota, period, consumption/reservation ledger | One quota definition; atomically reserve seats, listing/portal jobs and AI credits; release cancelled reservations; no unbounded null without negotiated policy |
| MaxPro Subscription | Organization + Plan version + entitlement overrides, lifecycle, period, billing references | Server-owned commercial state; downgrade preview differs from applied change; payment webhook settlement only after gateway approval |
| MaxPro Verification | Organization + optional Property/revision, evidence metadata, pending/approved/changes/rejected, reviewer, policy version, notes | Distinguish legal verification from internal approval. Revision changes invalidate dependent receipts; restrict evidence access |
| MaxPro Audit Event | Organization, authenticated actor/membership, command/request ID, target/revision, action/outcome, timestamp, redacted diff | Server-generated append-only business ledger; retention, restricted access, export integrity; no credentials or message bodies in audit |

Frappe User/session and role permission metadata are identity authority. Frontend tables, inspectors, capability display, queue filters, ROI cohorts, upgrade previews and deterministic demo persona selector are **views**, never authoritative records. The browser-local envelope and fictional aliases are fixtures; do not migrate them into production accounts or legal evidence. Frontend moderation is not permission to publish commercially.

## Permissions and organization isolation

Map private landlord, independent broker, agency agent, manager, owner and super administrator to explicit Frappe roles plus active Membership. The centralized prototype matrix in `organization-engine.ts` specifies UX examples: agents edit properties/work leads/draft campaigns; managers additionally assign/review campaigns/manage team; owners additionally manage billing/profile; super administrators configure plans, moderate and administer organizations. Landlord/broker operate their own business. Final scopes (especially agent own/assigned records and manager owner changes) require security review; do not translate UI visibility into authorization.

On every read/list/write/export/file/job/RPC: derive user from authenticated Frappe session, resolve active membership and authorized organization, enforce role and document ownership, then validate linked organization IDs. Apply `permission_query_conditions` and `has_permission` hooks/document permissions as appropriate. Generic REST list filters alone cannot isolate tenants. Avoid bypass APIs (`get_all`, `ignore_permissions`, unscoped SQL) in user paths. Whitelisting a method alone does not authorize its records. Platform administration requires explicit elevated role, reason and audit; never use implicit client-selected role escalation. Phase 6 adds a browser-local operational organization switcher. It is UX simulation, not a secure tenant boundary.

Session strategy must specify secure HTTP-only cookies, CSRF enforcement, deployment origin/CORS, logout/revocation, MFA for administrators, invitation tokens/expiry and file visibility. Browser actor/organization fields are assertions to validate, not authority. Do not ship API secrets to the frontend. An optional Next server boundary can proxy approved session requests; it does not replace Frappe authorization or introduce a second backend framework.

## Data access and API contracts

`src/lib/prototype-repository.ts` is the typed frontend boundary, implemented only by injected browser-local store functions. Existing domain DTOs remain independent of Frappe's `name`, `modified`, `data` resource envelope and `message` RPC envelope. A future Frappe adapter will map these shapes into stable IDs, revision/etag and discriminated errors (`forbidden`, `conflict`, `validation`, `capacity`, `unavailable`). Never import vendor connector adapters into UI.

Proposed authenticated request envelope: `{command, expectedRevision, idempotencyKey}`. Server derives actor/membership/org and returns `{data, error, requestId, revision}` using an agreed API version. Field errors map to forms; 403 shows denied, 409 reload/review conflict, 422 validation, 429 retry-after, transient errors preserve draft and require explicit retry. Define pagination/cursors, filtering, ordering and redaction for every query. Browser local adapter is synchronous in mutation semantics; async facade does not claim durable network retries, cross-user locking or idempotency.

| Operation | Proposed API path / ownership |
|---|---|
| Read authorized organization/member/property/plan/job/review records | Frappe document API (`GET /api/resource/<DocType>` and `/<name>`) with list/document/file permission enforcement, explicit safe fields and pagination |
| Update low-risk profile/preferences/draft metadata | Document API `PUT /api/resource/<DocType>/<name>` only where controller validation, revision checks and hooks enforce invariants; prohibit status/approval/plan bypass via generic writes |
| Create organization + owner, invite/accept/change membership, reserve/release seats | Custom authenticated POST whitelisted `maxpro.api.organizations.*`; transact related records, last-owner and entitlement constraints |
| Revise canonical property/media and invalidate approvals | Custom `maxpro.api.properties.revise`; expected revision, affected reviews/campaigns and audit in one transaction; draft creation can use document API if controller enforces same policy |
| Validate/approve/queue/retry/cancel publication, rotate feed access | Custom `maxpro.api.publishing.*`; validate exact revision/destinations/config/permissions, reserve quotas, create job/outbox atomically |
| Ingest provider events, dedupe/assign lead, send approved reply, reserve viewing | Custom `maxpro.api.crm.*`; signed intake for external webhooks, authenticated commands for users; atomic cursor, consent and scheduling |
| Propose/edit/approve/simulate real campaign replacement, authorize spend | Custom `maxpro.api.campaigns.*`; separate proposal generation from approval/dispatch, protect ordered revision receipts and budget ceilings |
| Quote/change plan, configure entitlement version, settle billing | Custom `maxpro.api.billing.*`; preview read-only, transactionally apply signed commercial state; payment settlement requires future verified gateway webhook |
| Moderate/verify/reject, change operational policies, inspect privileged audit | Custom `maxpro.api.admin.*`; note/reason, permission/policy and revision checks; generic document CRUD cannot grant approval |

Endpoints are proposed design names, not callable APIs. No frontend fetch or network mutation is added in Phase 5. Do not store browser demo permissions as Frappe session privileges.

## Transactions, concurrency and workers

Use expected revision/modified checks for drafts and membership/settings, lock or equivalent transactional serialization for tenant quota rows, round-robin cursor, last-owner removal, booking slots and approval consumption. Reserve capacity and append audit/outbox in the same transaction as a command. Use uniqueness for organization/source/event intake and organization/destination/property-revision/payload intent. An idempotency receipt stores command digest/outcome; same key with a different body conflicts. A retry must not duplicate charge, assignment or publishing job. Design consistent lock ordering and backoff; test concurrent plan downgrade vs invitation/publish, edit vs approval/dispatch, duplicate webhook, and retry vs cancel.

Frappe background jobs/workers process only committed outbox intents (`enqueue_after_commit` or reviewed equivalent). Workers recheck current membership/policy/entitlement/approval revisions before external dispatch, resolve server credentials, enforce organization/provider rate limits, retry transient failures with bounded backoff, quarantine permanent failures and audit attempts. Separate queues may handle media processing, partner publishing/feed refresh, inbound lead normalization, messaging, marketing, AI and reconciliation. Schedules monitor stalled jobs and fetch acknowledgement states. No worker may promote queued to accepted without partner evidence. Remote acceptance after cancellation needs reconciliation/compensation rather than history rewriting.

Media tasks require malware/EXIF/privacy review, authorized object storage/File permissions and checksum/version handling. AI tasks require grounding, human review, credit reservation/settlement, provider policy, evaluations and trace redaction. Real billing and marketing spend remain disabled until commercial/legal/partner approval. Worker serialization and multi-site/tenant deployment choice need load/security testing.

## Phase 6 gates

Phase 6 remains frontend-only. Before a separately authorized backend phase, pin independently verified Frappe/database/deployment versions, approve schema/role/organization isolation design, obtain independent architecture/security review, implement an isolated authenticated development app with migrations and test fixtures, then prove cross-tenant read/list/write/file/RPC/job denial and concurrent quota/approval invariants. Port local DTOs and tests behind the same frontend boundary. Add durable audit/outbox and recovery, backups/restore, observability, privacy/retention and bilingual UAT. Select one officially authorized provider sandbox only after account/contract approvals. No live integrations or payments follow automatically from this document.
